CI workflows¶

PolicyStack's GitHub Actions workflows live in .github/workflows/. Four of them check a fleet repository and run unchanged in yours: copier copies them with the framework, and framework updates change them, so don't edit them (Tiers). Upstream (upstream.yml) checks PolicyStack itself and runs only in upstream PolicyStack. For an adopter, the checks that cover real clusters are the fleet/ pass of Policy Validate and Render Diff; the rest guard the framework. A repository hosted on GitLab runs the same adopter checks from .gitlab-ci.yml (GitLab CI).

Workflow Trigger Fails when In your repository
CI (ci.yml) Every PR and main push A hook, the secret scan or the validator fails Runs
PR Title (pr-title.yml) Every PR, including title edits The title is not a Conventional Commit Runs
Policy Validate (validate.yml) Called by CI A validator error, a bad fleet pin, a broken install chart Runs, including the fleet/ pass
Render Diff (render-diff.yml) PRs into the default branch changing stack/, lifecycle/, lib/, values/, values.yaml, fleet/, tools/validator/ or Render Diff itself Never: it only comments Comments only when fleet/ has files, so only in yours
Upstream (upstream.yml) Every PR and main push The policy-library lint or tests, a validator lint or test, a stale CRD, the doc generator tests or the site build fails Absent: copier leaves it out
Stable (stable.yml, stable-review.yml) PRs into main Never fails on a change: the required stable status waits for a maintainer's sign-off Absent: copier leaves it out

A new push to a PR cancels its running CI, Upstream and Render Diff checks. CI, Upstream and Policy Validate can also be started from the Actions tab.

Required checks¶

A required check is one GitHub won't let a PR merge without. ci and pr-title are the required checks for main, set in a GitHub repository ruleset. Rulesets live in the repository settings, not in the files copier copies, so your repository has none until you add one: without it, a red PR still merges. Create a branch ruleset on the default branch that requires the status checks ci and pr-title (Protect the repository has the steps, plus code owner review on fleet/). The ruleset matches checks by job name, so renaming ci or pr-title leaves PRs waiting on a check that never reports.

ci is the last job in ci.yml. It always runs and fails if any job it needs failed, was cancelled or was skipped (alls-green). A new job goes in its needs, not in the ruleset.

Upstream PolicyStack's ruleset requires two more: upstream, the same kind of last job in upstream.yml, and stable, a commit status Stable sets. A job in one workflow can't wait on a job in another, and ci.yml can't call upstream.yml because that file is missing from your repository, so upstream PRs are gated by the checks together.

Note

No gating workflow has a paths filter. A required check whose workflow is skipped by on.paths never reports, so the PR waits on it forever.

CI (ci.yml)¶

Job Runs
lint prek run --all-files --show-diff-on-failure: the hooks in .pre-commit-config.yaml. It installs only the hooks' tools from mise.toml. On a PR, then the secret scan of the PR's commits
validate Policy Validate
ci The required check over lint and validate

Tool versions come from mise.toml. Run the same checks locally: Setup.

Hooks¶

prek is a pre-commit-compatible hook runner, installed by mise install. It reads .pre-commit-config.yaml; you don't need pre-commit itself.

Hook Checks
check-yaml, trailing-whitespace, end-of-file-fixer, check-merge-conflict, check-added-large-files prek builtins. check-merge-conflict runs with --assume-in-merge, so it also fails conflict markers committed after an update
actionlint (workflow syntax), zizmor (workflow security audit) Workflows. zizmor runs offline
gitleaks Staged changes, for secrets (Secret scan). Never the whole tree, even under --all-files
shellcheck Shell scripts
ruff-check, ruff-format Every Python file (tools/*.py, tools/policystack/)
element-readmes Regenerates stack/*/README.md, except for elements with a .copier-answers.yml: their README is upstream's (Element reference)
lychee Link checker: relative links in docs/, offline

check-yaml, trailing-whitespace, end-of-file-fixer and check-added-large-files skip templates/, converters/ and __snapshot__/, which are YAML only once rendered. check-merge-conflict checks them too. Every hook skips tools/validator/crds/, which holds upstream's files as fetched.

A hook that rewrites a file (trailing-whitespace, end-of-file-fixer, ruff-format, element-readmes) fails. Commit what it wrote:

prek run --all-files   # rewrites what it can
git add -u             # stage the rewritten files; add a new element's README by path

Tip

prek install runs the hooks on every commit.

Secret scan¶

gitleaks looks for credentials: API keys, tokens, private keys, and base64 data in Secret manifests. A plaintext stringData value is caught only when it looks like a key. Rules are gitleaks' defaults plus the allowlist in .gitleaks.toml. There are no PII, IP address or email rules, because values hold them.

Where Scans
lint job, PRs only Every commit between the PR's base and head, merges included (diffed against their first parent, so a conflict resolution counts)
gitleaks hook Staged changes, at commit time after prek install, or under prek run. CI stages nothing, so there it scans nothing

A secret that one commit adds and a later commit removes still fails the PR: it stays in the branch history. Rotate it, then rewrite the branch without it. Pushes to main aren't scanned again. With the ruleset from Required checks, every commit reaches main through a PR; without it, a direct push is never scanned.

Redaction

--redact replaces the secret in the log. A match that spans lines, such as a Secret manifest from kind: Secret to data:, prints its other lines as they are, stringData values included.

To scan your branch's commits locally:

gitleaks git --log-opts="--diff-merges=first-parent origin/main..HEAD" --redact

False positives¶

.gitleaks.toml is framework, so don't edit it. For a false positive in your files, end the line with a gitleaks:allow comment:

imageDigestKey: 9f8a7c6b5d4e3f2a1b0c9d8e7f6a5b4c # gitleaks:allow

Inside a block scalar (| or >) the comment would become part of the value. There, add the finding's <file>:<rule>:<line> to .gitleaksignore at the repository root instead, one per line, for example values/clusters/prod.yaml:generic-api-key:12. The scan output prints each finding's file, rule and line. An entry matches by line number, so it stops matching when the line moves.

Upstream¶

upstream.yml checks PolicyStack itself (the library, the validator code, the launcher and the docs site), then publishes the site and cuts releases. It runs on every PR and main push in upstream PolicyStack. copier leaves it out of an adopter's copy, so none of this runs there.

Job Runs
library policy-library in lib/: ct lint --config lib/ct.yaml, which fails a change to lib/policy-library without a version bump and runs helm lint --strict; then the helm-unittest suites in lib/tests (untt --strict), failing on a snapshot that is not committed (Library changes)
validator make -C tools/validator lint (golangci-lint, go mod tidy -diff, govulncheck) and test; the Stable gate's tests (.github/scripts/stable-gate-test.sh); then make crds, failing when tools/validator/crds/ differs from the files the Makefile pins (CRD schemas)
launcher uv lock --check (tools/policystack/uv.lock matches pyproject.toml), then the launcher's tests (pytest tools/policystack/tests): unit tests, generic checks of this checkout's stack/ and values/, and install, add and update run end to end through copier against a synthetic upstream that uses this checkout's copier.yml
docs Doc generator tests (python -m unittest tools/test_doc_generator.py), then zensical build --strict
upstream The required check over library, validator, launcher and docs
release main pushes in PolicyStack/PolicyStack only, after upstream: release-please opens or updates the release PR and, once it merges, tags it vX.Y.Z (Releases)
pages After release: builds the versioned site with mike (Documentation site)
publish After pages: pushes the site to gh-pages

Documentation site¶

The docs job builds docs/ with zensical build --strict, which fails on a relative .md link or anchor that doesn't resolve, or a missing snippet file.

The published site is versioned, so readers see the docs of the release they run, not of main:

Path Built from Updated
/dev/ main Every main push
/X.Y/ The newest vX.Y.Z tag of that minor When a release is tagged
/latest/ A copy of the newest /X.Y/ With it. / redirects here

On every main push, pages rebuilds dev and looks up the newest vX.Y.Z tag. If versions.json on gh-pages doesn't list that release as latest, it builds the tag as X.Y and moves latest to it. It checks the tag on each run instead of reacting to the release, so a release whose pages or publish failed is deployed by the next main push. Prereleases (vX.Y.Z-rc.N) get no version; dev covers them.

publish then replaces gh-pages with a single commit, using a GitHub App. Argo CD repo-servers fetch every branch, so the built HTML keeps no history. .github/pages/404.html becomes the root 404 page: it redirects an unversioned link, such as /start/install/ in a README or a Chart.yaml home, to the same path under /latest/.

Docs changes reach /latest/ with the next release

Each version is built from its tag. A docs fix merged to main shows on /dev/ at once and on /latest/ with the next release. docs/ changes alone don't cut a release (Releases).

Not checked by strict mode

Absolute links, nav and the content of included snippets (Docs layout).

Stable¶

Upstream only. A stable element changes incompatibly only in a major. This check makes sure no PR changes one without a maintainer seeing exactly what changed and signing off, whoever wrote it.

Part Does
stable.yml Runs on the PR and hands its number to stable-review.yml. Runs no PR code
stable-review.yml check Runs .github/scripts/stable-gate.sh from main, comparing every element that is stable at the merge base, or becomes stable, between the merge base and the PR. Read-only token
report Comments the findings, or deletes an earlier comment when there are none, and sets the commit status stable
sign-off Waits for a reviewer of the stable-change environment, then sets stable to success. Refuses an approval from the PR's author

stable-review.yml runs on workflow_run, so GitHub always takes it, and the gate script, from main: a PR can't edit the check that judges it, and fork PRs get the comment, which a pull_request workflow's read-only token can't write. A PR that breaks or edits stable.yml only leaves stable unset, and the PR can't merge.

The comment sorts findings into three tables:

Table Found by Means
Breaking Comparing files: the element removed or no longer stable; a config key removed or its type changed; a policy, template or operator entry removed or renamed, converter file names included; enabled, remediationAction, complianceType or pruneObjectBehavior changed where the entry exists on both sides; the library floor on a new major. Comparing renders: an object or policy template that no longer renders, a render that now fails, and a Policy's disabled, remediationAction, complianceType or pruneObjectBehavior rendered differently, whether the change comes from the element, a converter or policy-library. A dependency that stops resolving (POLICY011), such as acm observability on odf ready, whatever the other element's stability A break as Element stability defines it. It merges with ! in the title. Sign off without ! only for a false positive, or a security fix titled fix(<element>): breaking:
Output changed for unchanged values Comparing renders: an object that changes, or a new one on by default Breaking, unless it is a named bug fix, an operator channel or version move, or a new entry that ships off or inform-only. A maintainer decides
Promoted stable set on an element From the next release it follows the stable rules

Each element renders turned on, three ways, as Policy Validate does: the fixture fleet with its values, everything on (--all-on with inputs.yaml), and each profile. Both sides use the merge base's values/ and tools/validator/testdata/, so a PR can't hide a change by editing the test values. In the everything-on and profile renders, new entries and the PlacementBinding subjects naming them are left out: they ship off.

The status is pending while findings wait for a sign-off, success without findings or once signed off, and failure when the check itself fails. Each push gets its own run and needs its own sign-off. To sign off, open the run from the comment, Review deployments, stable-change, Approve and deploy. The status names who approved.

Prevent self-review stops whoever triggered the run from approving it. A workflow_run run takes its actor from the PR run that triggered it: the PR's last pusher, fork PRs included. When someone else pushed last, the author isn't stopped there, so sign-off refuses the author's approval itself. Re-run the job for another maintainer to approve.

Not seen

The check compares renders of upstream's test values. A branch of a converter no fixture reaches, a key that accepts fewer values (elements have no schema of allowed values), and what a change leaves on live clusters (a field musthave keeps after the converter stops setting it) are for the reviewer.

Setup¶

In PolicyStack/PolicyStack settings, once:

  1. Environments, new stable-change: required reviewers @PolicyStack/maintainers, Prevent self-review on, deployment branches main only. sign-off fails, leaving stable pending, while the environment lacks either.
  2. The main ruleset: require the status check stable, with GitHub Actions as its source.

PR Title¶

Squash merges make the PR title the commit subject and the release-note line, so it must match:

<type>(<scope>)!: <subject>

type is one of feat fix docs chore ci refactor test perf build revert. (<scope>) (lowercase, digits, -) and ! (breaking) are optional.

feat(validator): real POLICY080       # ok
fix!: rename hubName                  # ok
feat(odf): breaking: rename config.pools  # ok: preview break, a minor
Revert "feat: add metallb"            # fails: retitle to revert: feat: add metallb

Editing the title re-runs the check. Upstream, release-please reads the squash commits to pick each release's version and write its notes (Releases). In your repository the titles only keep history readable; if you don't want the check, drop pr-title from your ruleset.

Policy Validate¶

Runs the validator. Findings are annotated on the PR at the file and line to fix. Errors fail the job, warnings only annotate.

The job runs twice. The leg that counts uses the Helm in mise.toml, 3.18.4: Argo CD renders every element with the Helm bundled in OpenShift GitOps, and OpenShift GitOps 1.18, the oldest PolicyStack supports, bundles Helm 3.18.4, so a pass here means the hub renders it too. The second leg uses Helm 4.2.1 to preview the next GitOps Helm. It is advisory (continue-on-error): its failure shows on the PR but doesn't fail ci. It becomes required when Argo CD 3.5 ships in OpenShift GitOps or Helm 3 reaches end of life on 2027-02-10, whichever comes first.

make -C tools/validator validate   # (1)!
  1. Three validator passes (What validate runs). POLICY080 reads the committed CRDs, so the job needs no network beyond Go modules.

Note

The Helm floor in mise.toml moves only when the supported OpenShift GitOps floor does (Installation). Upstream's Renovate does not bump it.

Your fleet (POLICY052)¶

The fleet/ pass renders your fleet files from the PR's tree, not each file's revision: a cluster pinned to tag v1.0 is validated against the PR's code. POLICY052 checks the pin itself: that it resolves and that its commit has what the fleet file uses (Revision). In a copier copy it also reads the framework release in .copier-answers.yml at that commit: a revision a major newer than the PR's, or more than one major older, fails, since the hub's install chart renders only its own major and the one before. To see what a pinned cluster actually gets, read Render Diff.

Promotions (POLICY053)¶

A PR whose fleet file differs from the default branch's and pins another commit, such as a promotion from v1.4.0 to v1.5.0, also validates that commit: its stack/, lifecycle/, lib/ and values/, with the fleet file from the PR.

Finding at the pinned commit On the PR
The render fails (RENDER000), a safety rule fails (POLICY037, POLICY041, POLICY042), or the commit can't be read or loaded Error: blocks the promotion
Any other error Warning: a rule newer than the tag must not block a rollback to it

Only changed fleet files

A pin the PR doesn't touch is not validated again. Neither is a pinned branch that moves later: protect any branch a fleet file names and run CI on PRs to it.

Install chart (POLICY071)¶

install/ is run by hand on each hub, so nothing else renders it. Upstream checks it in the fixtures pass; your repository checks it in the fleet/ pass, so only once fleet/ has a file. It reads stack/acm and stack/gitops, which every repository needs. The check fails when:

  • helm lint install fails.
  • helm template install succeeds with an empty hubName or gitRepo. Neither has a usable default: hubName picks the hub's own fleet file and the clusters it builds, gitRepo is the repository Argo CD reads.
  • policyNamespace differs between install/values.yaml and values.yaml, which the elements read.
  • An ApplicationSet (or its Application template), the GitOpsCluster or its Placement lacks velero.io/exclude-from-backup: "true". ACM backup restores onto a passive hub, where a restored ApplicationSet would rebuild the old hub's clusters (Hub disaster recovery).
  • install/operators doesn't render the ACM and GitOps operators plus a MultiClusterHub (Installation).

Render Diff¶

Comments on the PR with what the merge changes in each fleet/ cluster's rendered Policies. Upstream ships no fleet files, so this only does something in your repository. It never blocks a merge.

### Fleet render: 3 cluster(s) change

> [!WARNING]
> `edge-3` pins `v1.4`, which is not a tag, branch or commit. Merging stops Argo CD from generating Applications for every cluster until it is fixed.

| Cluster | Revision | Changes |
|---|---|---|
| `prod-east-1` | `main` | user-monitoring: 1 Policy changed<br>metallb: 1 Policy added, 1 Policy removed<br>metallb: removes Policy `config-metallb-prod-east-1` |
| `nonprod-west-1` | `v1.0.0` → `main` | metallb: **render failed** |
| `edge-2` | new at `main` | 6 elements, 21 objects added |

What it renders¶

Each fleet file is rendered at its own revision, resolved as POLICY052 does, once before and once after the merge (.github/scripts/render-diff.sh). A cluster is rendered only when its resolved commit or its fleet file changes. So a cluster pinned to main or HEAD shows the PR's changes, and a cluster pinned to a tag shows changes only when the PR edits its fleet file (revision, valueFiles, version, channel, install, hub). lifecycle/ is rendered for fleet files that set hub. install/ is not rendered: a change there reaches every cluster at the next helm upgrade (Install chart).

It renders with the baseline selector, so Placements show name Exists, not the per-cluster selector. It checks only that the render succeeds: findings come from Policy Validate.

Reading the comment¶

Below the table, each cluster gets one collapsed block holding a diff per changed element, or the Helm error. render fixed means the element failed at the cluster's revision before the merge and renders now. removes Policy names each Policy the merge deletes from the hub, renames included: ACM names can't change, so a renamed Policy is deleted and recreated and starts its compliance history over. An element that fails the same way on both sides is not listed. A cluster added or removed shows totals only. A warning above the table flags a fleet file whose revision doesn't resolve or that the validator can't load at all. If it merges anyway, the ApplicationSet can't build its list of Applications: it deletes nothing, but no change reaches any cluster until the fleet file is fixed (Generators).

No fleet files, or no cluster whose render changes, means no comment. The comment is sticky: a later push that changes nothing deletes it.

Limits

  • Comments stop near 60,000 characters. The full patch is the run's render-diff.patch artifact.
  • A PR from another repository (a personal fork of yours) gets a read-only token, so the result goes to the job summary instead of a comment.
  • About 30 seconds per distinct commit rendered.

GitLab CI¶

copier copies .gitlab-ci.yml into every repository, next to .github/. GitHub ignores it, and GitLab ignores .github/workflows/. It is framework, so don't edit it. It runs the adopter checks of CI, Policy Validate and Render Diff, with the same commands and the tool versions in mise.toml:

Job Pipelines Same as Fails the pipeline
validate Every MR, every push to the default branch, Build > Pipelines > New pipeline Policy Validate, Helm 3.18.4 Yes
validate (helm 4.2.1) The same Policy Validate's advisory leg No (allow_failure)
gitleaks Every MR The secret scan of every commit in the MR Yes
render-diff MRs into the default branch that change the paths in Render Diff, .gitlab-ci.yml included Render Diff, posted as an MR note No (allow_failure)

The hooks in CI lint and PR Title don't run on GitLab. Run the hooks locally with prek install (Hooks). There is no ci job either: the pipeline's own status is the gate. While Settings > CI/CD > General pipelines > Auto-cancel redundant pipelines is on, a new push to an MR cancels its running pipeline. Pushes to the default branch run to the end.

Every job runs in ghcr.io/jdx/mise, pinned by tag and digest, and installs only the tools it needs from mise.toml, plus make, jq and openssl from the image's Debian release, and yq at the version .gitlab-ci.yml pins. GitLab caches the tools and Go modules in .mise/ for each job.

Differences from GitHub:

  • Validator findings print as text in the job log, not as inline annotations.
  • GitLab Free runs an MR pipeline on the MR's last commit, not merged with its target (merged results pipelines are Premium). GitHub checks the merge, so validate and render-diff merge the MR into the target's tip themselves before they run. When that merge conflicts, both fail: validate blocks the MR, render-diff shows a warning. Resolve the conflict and push.
  • A fork's MR pipeline runs in the fork, so validate resolves fleet pins against the fork's branches and tags, and render-diff doesn't run. Change fleet/ from a branch in your project.
  • The full patch is the job's render-diff.patch artifact. The note's Full patch link opens the job's artifacts.
  • The note's text says "PR": it comes from the same script as the GitHub comment.

Merge gate¶

GitLab has no named required checks. A pipeline gates a merge once Pipelines must succeed is on. Set these up once, on any tier:

  1. Settings > Merge requests > Merge checks: turn on Pipelines must succeed. A pipeline that passed with warnings counts as succeeded, so the advisory jobs don't block.
  2. Settings > Repository > Protected branches: on the default branch, set Allowed to push and merge to No one and Allowed to merge to Maintainers. Every change then reaches the branch through an MR, so gitleaks scans every commit.

GitLab Free can't require review

Required approvals, approval rules and Require Code Owner approval need GitLab Premium or Ultimate. On Free, an approval is optional and never blocks a merge. Code owners are Premium too, and GitLab never reads .github/CODEOWNERS: it looks in the root, docs/ and .gitlab/. Anyone allowed to merge can merge an MR nobody else has read, fleet/ changes included. With Allowed to merge set to Maintainers, review comes down to your Maintainers' discipline. Protect the repository describes the GitHub ruleset this replaces.

Render Diff token¶

GitLab's job token can't write MR notes, so the note needs a token of its own. Without one, the result is only in the job log.

  1. Create a token with the api scope and the Reporter role on the project:
    • GitLab Self-Managed or Dedicated, any tier: a project access token (Settings > Access tokens).
    • GitLab.com Free: project access tokens need Premium, so use a service account (GitLab 18.11 or later): create one, add it to the project as Reporter, and create a personal access token for it. On Premium, a project access token works.
  2. Settings > CI/CD > Variables: add it as RENDER_DIFF_TOKEN, Masked, not Protected. MR pipelines from unprotected branches never get protected variables.

The note is sticky: later pushes update it, and the next run that finds no change deletes it. A run for an older push leaves the note alone. The job runs only while the MR changes a path it watches, so if a later push reverts every such change, delete the note by hand.

Who can read the token

Every job in an MR pipeline gets the variable, and the MR's own .gitlab-ci.yml decides what those jobs run. So anyone who can push a branch can read the token. That is why it gets the Reporter role: it can't do anything a member who pushes branches can't already do, while they are a member. A copied token outlives their membership, so give it an expiry date and rotate it when someone loses push access. By default a fork's MR pipeline runs in the fork, with the fork's variables, and skips render-diff. If a member runs a fork's pipeline in your project instead, the fork's .gitlab-ci.yml gets your variables, the token included.

Dependencies¶

Upstream, Renovate, a bot that opens dependency update PRs, bumps everything in the table below. Its config is the org preset renovate-config.json in PolicyStack/.github, which upstream's renovate.json extends. copier doesn't copy that file, and your repository runs no bot: the pins below reach you with framework updates (Upgrading PolicyStack).

Pinned in What
mise.toml Every CLI tool, Go and Python
tools/validator/go.mod Go libraries and govulncheck (go tool)
tools/requirements*.txt PyYAML, Zensical
tools/policystack/uv.lock copier, questionary, ruamel.yaml and their dependencies, for the launcher
.github/workflows/ Actions, by commit SHA
.gitlab-ci.yml The mise image, by tag and digest. The yq version in render-diff is bumped by hand
tools/validator/Makefile The CRD source SHAs. A bump needs make crds and the refetched tools/validator/crds/ committed on the PR (CRD schemas)

policy-library is not a dependency Renovate moves: it is lib/policy-library in this repo, and elements declare a floor on it (Library changes).
